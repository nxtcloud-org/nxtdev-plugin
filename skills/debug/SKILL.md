# Systematic Debugging

버그를 체계적으로 해결하는 워크플로우. 추측 기반 수정을 구조적으로 차단한다.

세 가지 목적:

1. 증상이 아니라 원인을 고친다.
2. 추측 기반 수정을 금지한다.
3. 고치기 전에 실패하는 테스트로 잠근다.

## Hard Gates

예외 없음.

0. **재현을 먼저 시도한다.** 재현 방법을 모르면 멈추고 `AskUserQuestion`으로 사용자에게 물어라.
1. **재현 가능/관찰 가능한 상태 없이 수정 금지.**
2. **근본 원인 가설 없이 수정 금지.**
3. **failing test 없이 수정 금지.**
4. **가설은 한 번에 하나만 검증.**
5. **수정 중 "여기 온 김에" 리팩토링 금지.**
6. **3번 수정 실패하면 구조적 문제를 의심.**

## When To Use

- 테스트 실패
- 로컬/프로덕션 버그
- 응답, 상태, 렌더링, 쿼리 결과가 기대와 다를 때
- 성능 저하, 타임아웃, 레이스 컨디션, 간헐적 실패
- 이전에 고쳤던 문제가 다시 발생

## When NOT To Use

- 새 기능 구현 (→ `/nxtdev:plan`)
- 요구사항이 불명확 (→ `/nxtdev:clarify`)
- 단순 설정 변경이나 오타 수정

## Required Output Contract

디버깅 완료 시 7가지 모두 충족:

1. **Problem statement**: 한 문장으로 정의
2. **Reproduction path**: 재현 방법
3. **Evidence**: 관찰된 결과
4. **Root-cause hypothesis**: 원인 가설
5. **Failing guard**: failing test, 재현 스크립트, 또는 로그 검증
6. **Fix**: 근본 원인을 겨냥한 단일 수정
7. **Verification**: 수정 후 재현 경로 + 테스트 결과

## Workflow

### Phase 0. 재현 시도 (MANDATORY)

**분석보다 먼저 재현을 시도한다.**

1. 실패하는 테스트/명령어가 있으면 실행
2. 없으면 최소한의 재현 스크립트 작성
3. 최근 코드 변경, 파일 상태, 환경 확인

**재현 방법을 모르면:**

→ 즉시 멈춘다. 분석으로 넘어가지 않는다.
→ `AskUserQuestion`으로 사용자에게 물어본다:
  - "이 이슈를 어떻게 재현할 수 있나요? 정확한 단계가 무엇인가요?"
  - "어떤 입력이나 환경에서 발생하나요?"
  - "항상 발생하나요, 간헐적인가요?"

**재현 환경이 복잡하면:**

→ 사용자에게 물어본다: "재현 환경 구성이 복잡합니다. 환경 셋업 계획을 만들까요?"
→ 동의하면 `/nxtdev:plan`으로 환경 구축 계획 작성
→ 거절하면 환경 요구사항을 문서화하고 로그/코드 분석으로 진행

### Phase 1. 문제 정의

문제를 한 문장으로 압축한다.

- 기대 동작
- 실제 동작
- 영향 범위
- 항상 재현 vs 간헐적

```text
Problem: <expected> but got <actual> under <condition>
```

증상과 추측을 섞지 않는다.

```text
Good: Product detail API returns 500 when brand is null.
Bad: Serializer is broken because brand mapping seems wrong.
```

### Phase 2. 재현 또는 계측

고치기 전에 실패를 다시 볼 수 있어야 한다.

우선순위:
1. 기존 테스트로 재현
2. 최소한의 통합 테스트로 재현
3. 유닛 테스트로 재현
4. 재현 스크립트/명령어로 관찰
5. 로그/계측 추가 후 관찰

간헐적 실패: 로그, 입력값, 타임스탬프, 동시성 조건을 캡처하여 관찰 가능성을 높인다.

재현 실패 시 → 코드 수정 금지. 관찰 가능성을 먼저 높인다.

### Phase 3. 증거 수집

관찰 가능한 사실만 수집한다.

체크리스트:
- 전체 에러 메시지와 스택 트레이스
- 실패하는 입력값
- 최근 변경된 파일/커밋
- 환경/설정 차이
- 호출 경로와 데이터 흐름

다중 컴포넌트 문제는 각 경계에서 검사:
- 무엇이 들어왔는가
- 무엇이 나갔는가
- 어떤 값이 변환되었는가
- 어떤 조건에서 깨지는가

원인 위치를 특정하기 전에 수정하지 않는다. 상세한 추적 기법은 [root-cause-tracing.md](references/root-cause-tracing.md) 참조.

### Phase 4. 근본 원인 격리

가설을 정확히 하나만 세운다.

```text
Hypothesis: <root cause> because <evidence>
```

좋은 가설의 조건:
- 단일 원인을 지목
- 관찰된 증거와 연결
- 작은 실험으로 반증 가능

나쁜 가설:
- "어딘가에 비동기 이슈가 있는 것 같다"
- "직렬화 레이어 전체가 불안정하다"

에러가 스택 깊은 곳에 나타나면, 증상이 아니라 입력의 출처를 추적한다.

### Phase 5. 실패 잠금

고치기 전에 실패를 잠근다.

우선순위:
1. 자동화된 failing test
2. 기존 테스트에 회귀 케이스 추가
3. 최소 재현 스크립트
4. 로그/어서션을 통한 임시 검증

규칙:
- 가능하면 항상 자동 테스트 작성
- 수정 전에 반드시 실패해야 함
- 수정 후 같은 경로로 통과해야 함
- 테스트 이름이 무엇이 깨졌는지 드러내야 함

### Phase 6. 단일 수정

하나의 가설에 대응하는 수정만 적용한다.

허용:
- 원인을 직접 해결하는 최소 코드 변경
- 검증에 필요한 최소 지원 변경

금지:
- 여러 관련 수정 묶기
- 리팩토링과 수정 합치기
- 포매팅/정리/이름 변경 끼워넣기
- 증거 없는 null 가드 추가
- 예외 삼키기

수정 실패 시 → Phase 1 또는 Phase 3으로 즉시 복귀. 이전 가설은 틀렸다.

수정 후 방어적 검증 레이어 추가가 필요한지 판단한다. 상세 패턴은 [defense-in-depth.md](references/defense-in-depth.md) 참조.

### Phase 7. 검증 및 종료

모두 충족해야 종료:

1. 원래 재현 경로가 더 이상 실패하지 않음
2. Phase 5의 failing guard가 통과
3. 관련 테스트가 깨지지 않음
4. 수정이 증상이 아니라 원인을 차단한다고 설명 가능

간헐적 버그: 단일 통과로 불충분. 반복 실행 또는 다양한 조건에서 검증 필요.

## Stop Conditions

### 1. 재현 실패

여러 시도 후에도 재현 실패 시:
- 관찰 가능성이 부족한지 확인
- 환경 차이 확인
- 문제 정의 자체가 잘못되었는지 확인

재현 없이 코드 변경은 금지.

### 2. 3회 수정 실패

3회 연속 실패 → 현재 이해가 잘못되었거나 구조적 문제(공유 상태, 경계 설계, 책임 분리).

네 번째 패치가 아니라 구조적 논의가 필요. 사용자에게 에스컬레이션한다.

### 3. Failing guard 없음

failing test나 동등한 재현 메커니즘을 만들 수 없으면 완료 선언 불가. 최소한 재현 명령어와 관찰 결과를 남긴다.

## Red Flags

이런 생각이 들면 즉시 멈추고 이전 단계로 복귀:

- "이 한 줄만 바꾸면 될 거야"
- "로그는 나중에 보고 일단 고치자"
- "테스트는 나중에 추가하자"
- "이것도 같이 고치자"
- "에러가 안 나니까 원인은 몰라도 되지"

## Timing Anti-Patterns

테스트의 임의 delay(`setTimeout`, `sleep`)는 flaky test의 근본 원인이다. 실제 조건을 폴링하는 패턴을 사용한다. 상세 가이드는 [condition-based-waiting.md](references/condition-based-waiting.md) 참조.

## Minimal Checklist

- [ ] 재현을 먼저 시도했다 (또는 사용자에게 재현 방법을 물었다)
- [ ] 문제를 한 문장으로 정의했다
- [ ] 실패를 재현하거나 관찰 가능하게 만들었다
- [ ] 증거를 수집했다
- [ ] 단일 근본 원인 가설을 세웠다
- [ ] 수정 전에 failing guard를 만들었다
- [ ] 단일 수정만 적용했다
- [ ] 수정 후 같은 경로로 검증했다

## Transition

디버깅 완료 후:

- 수정 완료 → 결과를 사용자에게 보고
- 재현 환경 구축 필요 → `/nxtdev:plan`
- 구조적 문제 발견 → `/nxtdev:clarify`로 스코프 재정의

이 스킬은 **다음 스킬을 직접 호출하지 않는다.** 결과를 보고하고 사용자가 선택하게 한다.
